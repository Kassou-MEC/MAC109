What exactly is installed here?

Three things, all free: the .NET SDK (the engine — C#'s compiler and runtime), VS Code (the workshop), and C# Dev Kit (the extension that teaches VS Code to speak C#: colors, IntelliSense, error squiggles, and the ▶ Run button). The fourth ingredient, Avalonia — the box of GUI parts — isn't installed on the machine at all: in Level 3 you will add it to your project, and it downloads itself on first run. 2

Create the project — from absolutely zero

🐣

A C# project is a folder with two kinds of things inside: your code files (.cs) and a recipe card (.csproj) that tells the SDK how to build them. You're about to have the SDK generate one, using only clicks. Watch every step — creating projects is a skill you'll repeat all semester.

  1. In VS Code, choose File ▸ Close Folder if any old project is open — start from the empty Welcome window.
  2. Press Ctrl+Shift+P. The Command Palette drops down from the top — VS Code's magic box that can do anything.
  3. Type new project and choose “.NET: New Project…” (from C# Dev Kit).
  4. A list of templates appears — ready-made project shapes. Type console and pick Console App. (Yes, console — we'll upgrade it into a GUI ourselves. That's the point: you'll see exactly what makes a GUI app a GUI app.)
  5. Name the project exactly: MyStudioApp — then press Enter.
  6. For the location, click Choose folder ▸ open Documents ▸ click New folder ▸ name it MAC109 ▸ press Select Folder. (Documents. Not Downloads, not Desktop — Documents.)
  7. The palette shows a summary line — press Enter on Create project.
  8. When VS Code asks, click Open — and if a blue box asks "Do you trust the authors of the files in this folder?", click Yes, I trust the authors. The author is you.
What did the SDK just generate for me?

Open the Explorer (top icon, left bar) and look: a folder MyStudioApp containing Program.cs (one line of code: Console.WriteLine("Hello, World!");) and MyStudioApp.csproj (the recipe card — which .NET version, what kind of app). That's a complete, runnable program. Everything we build this semester grows from a seed exactly like this one — there is no other magic.

3

Add the Avalonia ingredients

🧂

A console app talks in text. To draw windows and buttons, we add Avalonia — a free box of cross-platform GUI parts — using NuGet, the app store for code libraries. Two packages, all clicks:

  1. Ctrl+Shift+P ▸ type nuget add ▸ choose “NuGet: Add NuGet Package…”. (If it asks which project: MyStudioApp.)
  2. Search Avalonia.Desktop ▸ select it ▸ pick the latest stable version (the top one, no "-preview" in the name).
  3. Repeat: palette ▸ NuGet: Add NuGet Package… ▸ search Avalonia.Themes.Fluent ▸ latest stable. This one makes your controls look modern instead of 1995.
  4. Now open MyStudioApp.csproj from the Explorer and read your recipe card — the two packages you just added are right there as <PackageReference> lines.
  5. One tiny edit while you're here: change <OutputType>Exe</OutputType> to <OutputType>WinExe</OutputType> and save (Ctrl+S). That tells Windows "this app has a window — don't open a black console behind it."
What is NuGet, really — and where does Avalonia "live"?

NuGet is the package manager for .NET: a giant free library of code other people wrote, versioned and downloadable. Adding a package writes one line into your .csproj — the actual code downloads into your project the first time you build (you'll watch it happen in Level 6 as "Restoring…"). That's why Avalonia isn't "installed on the machine": it travels inside your project. Anyone who opens your project on any OS gets the same ingredients automatically.

Meet the cockpit

🛩️

Before writing the real code, learn your instruments. Four areas of VS Code do almost everything this semester — find each one on your screen:

  • Program.cs 💜 — code. In Level 5 it becomes your app's engine.
  • MyStudioApp.csproj — the recipe card you already edited. Look, rarely touch.
  • bin & obj — robot-made folders where compiled output and downloaded packages land. Never edit — and in Level 12 you'll exclude them from your submission.

Where's the design file? Where's the drag-and-drop?

When Week 5's classes-and-objects lecture arrives, it will be naming things you've already done for a month.

5

The engine + the empty frame

🔧

Every GUI app in this course is exactly two files with two jobs:

  • ⚙️ Program.cs — the engine. Starts Avalonia and opens your window. You paste it once and never touch it again all semester. If you're editing Program.cs, something went wrong. 😄
  • 🪟 MainWindow.cs — YOUR file. Everything you build, today and every week until December, happens here. And today it starts almost empty — on purpose.
  1. In the Explorer, hover over the MyStudioApp folder — small icons appear. Click the New File… icon (📄+), name it exactly MainWindow.cs, press Enter.
  2. Copy in the tiny MainWindow below — read it, it's four lines of ideas — and save (Ctrl+S).
  3. Open Program.cs, select all (Ctrl+A), delete, paste the engine below, save. Done — you will not open this file again.
MainWindow.cs — YOUR file (new). This is the whole thing.
using Avalonia.Controls;

namespace MyStudioApp;

public class MainWindow : Window
{
    public MainWindow()
    {
        // Your app is built right here — one line at a time,
        // starting in Level 7. Empty for now, on purpose!
    }
}
Program.cs — the engine (replace everything). Copy once, never touch.
using System;
using Avalonia;
using Avalonia.Controls.ApplicationLifetimes;
using Avalonia.Themes.Fluent;

namespace MyStudioApp;

// PART 1 — The launcher. Starts Avalonia.
class Program
{
    [STAThread]
    public static void Main(string[] args)
    {
        AppBuilder.Configure<App>()
                  .UsePlatformDetect()
                  .StartWithClassicDesktopLifetime(args);
    }
}

// PART 2 — The app. Loads the modern theme, opens your window.
public class App : Application
{
    public override void OnFrameworkInitializationCompleted()
    {
        Styles.Add(new FluentTheme());

        if (ApplicationLifetime is IClassicDesktopStyleApplicationLifetime desktop)
        {
            desktop.MainWindow = new MainWindow();   // ← opens YOUR file
        }

        base.OnFrameworkInitializationCompleted();
    }
}
What do I need to understand today? (Honest answer: 4 lines)

Only MainWindow.cs, and it says exactly four things: my window is a Window (that's the : Window — it inherits everything a window can do); it lives in my project (namespace); and when it's created (public MainWindow() — the constructor), it does… nothing yet. The empty { } is your workshop.

Program.cs is the engine: launcher starts Avalonia, app loads the theme and opens your window. The only line worth pointing at is desktop.MainWindow = new MainWindow(); — the handshake between the engine and your file. Everything else: copy, wave politely, move on.

6

Press ▶ — a window is born

🎬
  1. With MainWindow.cs open, press F5 — or menu Run ▸ Start Debugging. If VS Code asks what kind of project, pick C#, then MyStudioApp.
  2. First run only: the status bar says Restoring… — that's Avalonia downloading itself into the project (the NuGet lines from Level 3, coming to life) — then Building…
  3. …and a window appears. Completely blank. Untitled. Perfect.
✅ Checkpoint — and the whole teaching trick of today: the window is blank because you haven't said anything yet. From this moment on, every single line you add will visibly change this window. One line, one F5, one change you can see. That's how we learn GUI: slowly, and with proof.
What did F5 actually do?

The whole Week 1 pipeline, for real: the compiler read your entire project and checked its grammar, translated it to universal IL, the .NET runtime JIT-translated that for this exact CPU, and the machine ran it. The same IL runs on Windows, macOS, and Linux — which is why your app is cross-platform without you doing anything.

7

Give it a title & a size

🏷️

Your first real GUI code: three properties, typed inside the constructor's { }. Type them — don't paste — and watch IntelliSense suggest as you go:

MainWindow.cs — inside public MainWindow() { … }
Title = "My Studio App — YOUR NAME";
Width = 500;
Height = 350;
  1. Type Ti and pause — IntelliSense offers Title. Press Tab to accept. Finish the line with your actual name inside the quotes, and end with a semicolon.
  2. Add Width and Height the same way. Numbers don't get quotes.
  3. Ctrl+S, then F5. 👀 Your name is in the title bar, and the window opens at exactly 500×350.
  4. Play scientist: change Height to 600, run. Change it back. Cause, effect, proof.
What is a "property," exactly?

Your window is an object, and objects carry properties — named settings you can read or change: Title, Width, Height… Setting one is just Name = value;. Notice the types matching: Title takes a string (quotes), Width takes a number (no quotes). Every control you meet from here — buttons, text boxes, all of them — works exactly this way. Learn this level, and you've learned half of GUI programming.

8

Paint it & put text inside

🎨

Two more moves: a background color (another property), and your first control — a TextBlock — placed inside the window.

Move 1 — paint. Add this line under Height:

MainWindow.cs — inside the constructor
Background = Brushes.MintCream;   // pick any: LightYellow, Lavender, Honeydew…
🩹 Red squiggle under Brushes? That's a missing using — colors live in the Avalonia.Media toolbox. Click the squiggle, press Ctrl+. (the Quick Fix menu), and accept using Avalonia.Media; — VS Code adds the line at the top for you. This trick fixes every "type not found" error you'll ever meet. After that, type Brushes. and pause: IntelliSense lists every color it knows. Shop around.

Move 2 — text inside. The window can hold content — give it a text object:

MainWindow.cs — under the Background line
Content = new TextBlock
{
    Text = "Welcome to MAC 109!",
    FontSize = 22,
    Foreground = Brushes.DarkSlateBlue,   // Foreground = the TEXT's color
    Margin = new Thickness(20)
};
  1. Read it before running: new TextBlock { … } creates an object and sets its properties in one go — Text, FontSize, Foreground (its color), Margin (breathing room). Same property idea as Level 7, new object.
  2. Content = hands that object to the window. (If Thickness gets a squiggle: Ctrl+. ▸ using Avalonia; — same trick.)
  3. F5 — painted window, message inside. Change the Text, the FontSize, both colors. Run after each change.
✅ Checkpoint: you now know the two verbs of GUI programming — set a property (Level 7) and create an object (this level). Everything else is combinations.
9

Add a button

🔘

A button is just another object — but there's a puzzle first: Content holds ONE thing, and we now want two (text and button). The answer is a StackPanel — a shelf that stacks its children top to bottom. Replace your whole Content = … block with:

MainWindow.cs — replace the Content block
var lblWelcome = new TextBlock
{
    Text = "Welcome to MAC 109!",
    FontSize = 22,
    Foreground = Brushes.DarkSlateBlue
};

var btnGreet = new Button { Content = "Say Hello" };

Content = new StackPanel
{
    Margin = new Thickness(20),
    Spacing = 12,
    Children = { lblWelcome, btnGreet }
};
  1. Notice the small refactor: the TextBlock now gets a name (lblWelcome, via var) so the shelf can refer to it. Naming convention all semester: lblText, btnButtons, txtTextBoxes.
  2. The button is one line: new Button { Content = "Say Hello" } — create the object, set its property. Level 8's two verbs, again.
  3. The StackPanel takes the Margin (the shelf carries the spacing now) and lists its Children in top-to-bottom order.
  4. F5 — there's your button. Now click it.
🤫 Why nothing? The button works — it's just deaf. Nobody told it what clicking should mean. Teaching a control to respond is called an event, it takes exactly one +=, and it's the whole next level. Best cliffhanger in programming.
10

Text box + your first event ⚡

💬

The finale of the build: a TextBox to type into, a TextBlock to answer in, and the += that wires the button's Click to a method of yours. Three additions:

Addition 1 — two controls that must survive after the constructor finishes, so they live at class level (right above public MainWindow()):

MainWindow.cs — above the constructor (fields)
TextBox txtName = new TextBox { Watermark = "Type your name…" };
TextBlock lblGreeting = new TextBlock { FontSize = 18, Foreground = Brushes.SeaGreen };

Addition 2 — subscribe the button and grow the shelf (inside the constructor):

MainWindow.cs — in the constructor
btnGreet.Click += BtnGreet_Click;   // "when clicked, run my method"

Content = new StackPanel
{
    Margin = new Thickness(20),
    Spacing = 12,
    Children = { lblWelcome, txtName, btnGreet, lblGreeting }
};

Addition 3 — the method itself, after the constructor, still inside the class:

MainWindow.cs — after the constructor
void BtnGreet_Click(object sender, RoutedEventArgs e)
{
    lblGreeting.Text = "Hello, " + txtName.Text + "!";
}
  1. Squiggle on RoutedEventArgs? You know the ritual: Ctrl+. ▸ using Avalonia.Interactivity;
  2. F5 ▸ type your name ▸ click Say Hello. The greeting appears on the window. Click again with a different name. Every click re-runs your method.
Why do txtName and lblGreeting live ABOVE the constructor?

Because two different moments need them: the constructor (to put them on the shelf, at startup) and BtnGreet_Click (to read and write them — possibly minutes later, every time the user clicks). Variables declared inside the constructor evaporate when it finishes. Declared at class level — as fields — they live as long as the window does. Rule of thumb: if the handler needs it, it's a field. lblWelcome and btnGreet stay as var locals because after setup, nobody needs to talk to them again… until next week, when we make btnGreet's Content change too. 😉

11

Add a Clear button — then break everything 😈

✨

Real apps reset. Add a second button with its own event — same pattern, zero new ideas, pure confidence:

MainWindow.cs — three additions
// 1 · in the constructor, next to btnGreet:
var btnClear = new Button { Content = "Clear" };
btnClear.Click += BtnClear_Click;

// 2 · grow the Children list:
Children = { lblWelcome, txtName, btnGreet, btnClear, lblGreeting }

// 3 · after BtnGreet_Click, its sibling:
void BtnClear_Click(object sender, RoutedEventArgs e)
{
    txtName.Text = "";        // empty the box
    lblGreeting.Text = "";    // hide the greeting
    txtName.Focus();          // cursor back home, ready for the next name
}

F5. Greet ▸ the label lights up. Clear ▸ everything resets and the cursor jumps home. Two buttons, two subscriptions, two handlers — the pattern scales to every feature you'll ever add.

Now, professionals sabotage on purpose. After each experiment, Ctrl+Z and confirm F5 still works:

  • 🔡 Change TextBlock to textBlock — instant red squiggle, and the Problems panel reports the type can't be found, with the exact line. Case-sensitivity!
  • ✂️ Delete the semicolon after the Title line — ; expected, again with the line number.
  • 💥 Delete one closing quote from "Say Hello" — suddenly many errors. One missing quote confuses everything after it. Pro ritual: fix the FIRST error first; the rest usually vanish.
  • 🕳️ All fixed? One last test, no code broken: run, leave the box empty, click Say Hello. "Hello, !" — slightly tragic. Nothing crashed, but it isn't smart either. Week 3's if statement fixes exactly this. Remember this moment.
Why celebrate errors?

These are compile-time errors — caught before anything ran, each with a reason and a line number. That's a gift, and it's why we use a compiled language: mistakes surface immediately instead of hiding until the worst moment. Reading errors calmly, top to bottom, first one first, is the most valuable habit you'll build this semester.

Why delete bin and obj? And why keep my own copy?

bin/obj hold compiled output plus the downloaded Avalonia packages — often 100+ MB of files your recipe card can regenerate anywhere in seconds (that's what "Restoring…" was). Submitting them is like mailing someone a cake and the dirty mixing bowls. Your own copy matters because lab machines are wiped: next Friday you'll download your latest ZIP (from your email/OneDrive or your own Brightspace submission), unzip it into Documents\MAC109, open it in VS Code, and keep building. That download-work-ZIP-upload loop is the weekly heartbeat of this course.

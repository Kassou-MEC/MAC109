Install the .NET SDK

🧰

The SDK is the engine that turns your C# into a running program — it contains the compiler and the runtime from the Week 1 deck. One-time install: download, double-click, done. And yes, it's completely free.

  1. In your browser, go to dotnet.microsoft.com/download.
  2. Click the big Download .NET SDK button (the SDK, not the "Runtime" — you're a developer now).
  3. Pick your machine: Windows → the x64 installer. Mac → Arm64 for any Apple Silicon Mac (M1–M4); x64 only for old Intel Macs. Linux → follow the Linux instructions linked on that same page for your distribution.
  4. Run the downloaded installer and click Continue/Next until it says installed. All defaults are perfect.
Why do I need this if I'm about to install VS Code too?

Kitchen analogy: VS Code is the countertop — a lovely place to work — but the SDK is the oven 🔥. Without it, nothing cooks. The SDK is C# on your machine: the compiler (the grammar-checker-translator) and the runtime that executes your program. VS Code just presses its buttons for you. Install both, and your computer officially speaks C# — whether it runs Windows, macOS, or Linux.

Install Visual Studio Code

💻

VS Code is your workshop for the semester — a free code editor that is identical on Windows, macOS, and Linux. Whatever computer you own, your screen will match your classmates' and the lecture slides.

  1. Go to code.visualstudio.com and click the big Download button — it auto-detects your operating system.
  2. Windows: run the installer, keep every default. Mac: the download is the app itself — drag Visual Studio Code into your Applications folder, then open it. Linux: grab the .deb/.rpm from the same page (or your software store) and install.
  3. Open VS Code once so it settles in. A Welcome tab appears — you can close it.
💡 Already have VS Code from another class? You're done — skip to Level 3. And no account or sign-in is ever required for anything in this course's setup.
Is VS Code the same as Visual Studio?

Different tools, confusing names. Visual Studio is a Windows-only heavyweight. Visual Studio Code is its lightweight sibling that runs everywhere — and once we add the C# extension in Level 3, it becomes a full IDE: editor + compiler buttons + debugger + Git, all in one window. One workshop for the whole class, no matter the machine.

Give VS Code its C# brain

🧠

Fresh VS Code doesn't speak C#. The free C# Dev Kit extension (by Microsoft) teaches it everything: rainbow syntax colors, IntelliSense autocomplete, error squiggles, a Solution Explorer, and — most importantly for us — the ▶ Run button.

  1. In VS Code, click the Extensions icon in the left bar (four squares, one flying away) — or press ⇧ ⌘ X on Mac / Ctrl ⇧ X on Windows & Linux.
  2. In the search box, type C# Dev Kit.
  3. Click Install on the top result, published by Microsoft. It automatically brings its friend, the base "C#" extension.
  4. When it finishes, a new Solution Explorer icon appears — that's your sign it worked.
✅ Checkpoint: Extensions ▸ Installed now lists "C# Dev Kit". High five — with the SDK (Level 1) + VS Code (Level 2) + this brain, your machine is a complete C# development studio, forever. Everything from here is the fun part.

Meet your project

Click the Explorer icon (top of the left bar). Your cloned folder holds a small family of files — here's who's who:

  • MainWindow.cs — YOUR window: the interface and the logic, in one C# file. This is where you'll live for weeks.
  • Program.cs — the ignition: it starts the app and shows your MainWindow. Look, don't touch.

Wait — when do I install Avalonia UI?

Surprise: you already arranged it. Avalonia isn't an app you install like VS Code — it's a package your project asks for, listed in one line of the .csproj recipe. The very first time you press ▶ Run, the .NET SDK reads that recipe and downloads Avalonia automatically (you'll see "Restoring…" flash by — that's it arriving). This is how professionals ship libraries: the project carries its own shopping list, so it builds the same on every machine and every operating system.

Make it yours

✍️

MainWindow.cs is the exact file from the lecture's First Code tab — go click through those line-by-line explanations if you haven't. Now edit it for the first time:

MainWindow.cs — the starter shell (what you cloned)
using Avalonia;
using Avalonia.Controls;

namespace MyStudioApp;

public class MainWindow : Window
{
    public MainWindow()
    {
        Title = "My Studio App";
        Width = 500; Height = 350;

        var lblWelcome = new TextBlock { Text = "Welcome to MAC 109!", FontSize = 22 };

        Content = new StackPanel
        {
            Margin = new Thickness(20), Spacing = 12,
            Children = { lblWelcome }
        };
    }
}
  1. Change the Title string to "My Studio App — YOUR NAME". Keep the quotes!
  2. Change the welcome Text to a greeting of your own.
  3. Press F5. Your name is now in a title bar. Officially a developer. 😎
Remind me — why no separate design file?

Because in this course, the UI is C# objects. new TextBlock { … } creates a control and sets its properties in one move (an object initializer), and the StackPanel's Children list is your layout — top-to-bottom, in list order. One file, one language, and every edit you just made was real C#.

8

Build the Greeter

💬

The beating heart of Milestone 1: a button that answers. You'll add four things — two fields, a Button, and the event wiring — turning the shell into the lecture's full program:

MainWindow.cs — the complete Greeter (your target)
using Avalonia;
using Avalonia.Controls;
using Avalonia.Interactivity;

namespace MyStudioApp;

public class MainWindow : Window
{
    TextBox txtName = new TextBox { Watermark = "Type your name…" };
    TextBlock lblGreeting = new TextBlock { FontSize = 18 };

    public MainWindow()
    {
        Title = "My Studio App — Maria";
        Width = 500; Height = 350;

        var lblWelcome = new TextBlock { Text = "Welcome to MAC 109!", FontSize = 22 };
        var btnGreet = new Button { Content = "Say Hello" };
        btnGreet.Click += BtnGreet_Click;

        Content = new StackPanel
        {
            Margin = new Thickness(20), Spacing = 12,
            Children = { lblWelcome, txtName, btnGreet, lblGreeting }
        };
    }

    void BtnGreet_Click(object sender, RoutedEventArgs e)
    {
        lblGreeting.Text = "Hello, " + txtName.Text + "!";
    }
}
  1. Add the third using line at the top — the handler's RoutedEventArgs lives there.
  2. Add the two field lines (txtName, lblGreeting) just above the constructor. Type them — feel the IntelliSense menu appear after every dot and new.
  3. Inside the constructor, add the btnGreet line and the Click += wiring line.
  4. Update the Children list to hold all four controls, in order.
  5. Add the BtnGreet_Click method after the constructor. Then F5 ▸ type your name ▸ click Say Hello.

Three new ideas 💥

  • Fields vs var: txtName and lblGreeting are declared at class level (fields) so the handler can reach them later. lblWelcome and btnGreet are var locals — nobody needs them after setup.
  • The += subscription: btnGreet.Click += BtnGreet_Click; means "when this button is clicked, run that method." Your program now waits for the user — that's event-driven programming.
  • Read → glue → write: the handler reads txtName.Text, glues strings with +, and writes lblGreeting.Text. That rhythm is 90% of GUI code.
✅ DELIVERABLE: the greeting appears on the window itself. That is the working core of Milestone 1 — everything left is polish and publishing.
9

Try to break it 😈

🔨

Professionals test on purpose. Run three sabotage experiments — and after each one, undo (⌘ Z / Ctrl Z) and confirm F5 works again:

  1. 🔡 Change TextBlock to textBlock (lowercase t). A red squiggle appears instantly, and the Problems panel says the type textBlock could not be found. C# is case-sensitive — Rule 2 from the lecture.
  2. ✂️ Delete the semicolon at the end of the Title line. The Problems panel points at the exact spot: ; expected.
  3. 💥 Delete one closing quote from "Say Hello". Suddenly many errors appear at once — one missing quote confuses everything after it. The pro move: fix the FIRST error first; the rest usually vanish.
  4. 🕳️ Everything fixed? One last experiment, no code broken: run the app, leave the box empty, click Say Hello. "Hello, !" — slightly tragic. Nothing crashed, but it's not smart either. Week 3's if statement fixes exactly this. Remember this moment.
Why celebrate errors?

Because these are compile-time errors — the compiler catching mistakes before anything runs, with a file, a line number, and a reason. That's a gift. Reading error messages calmly (top to bottom, first error first) is the single most valuable habit you'll build this semester. The squiggle is not judging you; it's helping.

Push your milestone — with buttons only

💡 Commit early, commit often. Every week's milestone is exactly these steps with a new message — and your commit history counts toward participation. A dead laptop can't eat homework that lives on GitHub.
Commit vs push — 15-second version

Commit = a labeled snapshot 📸 of your code on your machine. Push (part of Sync Changes) = uploading your snapshots to GitHub, where they survive spilled coffee, stolen backpacks, and "my computer died." A commit without a push is a photo saved on a camera nobody can see.

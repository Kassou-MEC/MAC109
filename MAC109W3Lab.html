Launch Visual Studio & create the project

🚀— ▢ ✕

At home on your Mac you used VS Code. The classroom machines run its big sibling, Visual Studio 2022 — the full professional IDE, and the reason this course is called Visual C#. Everything is pre-installed. Let's make a project.

  1. Log into the lab machine, press the ⊞ Windows key, type Visual Studio, and open Visual Studio 2022 (the purple ∞ icon — not the blue VS Code one).
  2. On the start window, click Create a new project.
  3. In the search box at the top, type winforms.
  4. Choose Windows Forms App — the one tagged C#. ⚠️ Skip the look-alikes: not Visual Basic, and not the one that says (.NET Framework). Click Next.
  5. Project name: Lab03_FirstGUI  ·  Solution name: MAC109_GuiLabs  ·  Location: Documents ▸ MAC109 (create the folder if it's not there). Click Next, keep the suggested .NET version, click Create.
🧠 Lab-machine reality check: these computers can be wiped between classes. Anything that only lives in Documents can vanish. That's why Level 10 — pushing to GitHub — is not optional today. You've been warned (lovingly).
What's the difference between Visual Studio and VS Code?
VS Code is a lightweight editor that learns C# through extensions — great on any machine, including your Mac. Visual Studio is the full workshop: it ships with the compiler, the debugger, and — the star of today — the Forms Designer, a canvas where you draw your program's window. The C# language is 100% identical in both. Same engine, fancier steering wheel.

Meet the cockpit

🛩️— ▢ ✕

Visual Studio opens with your project, and in the middle sits something new: a blank grey window called Form1. That's not a picture — that's your program, being designed live. Find these four panels before touching anything:

  • Designer canvas 💜 (center) — Form1, the window you are building. Today's main stage.
  • Toolbox (left) — a parts shelf full of controls: buttons, labels, text boxes… you'll drag these onto the form.
  • Properties window (bottom-right) — every knob and dial of whatever is selected: its text, color, size, name.
  • Solution Explorer (top-right) — your files. Form1.cs holds your code; Program.cs just starts the app. Look, don't touch.
Wait — a "Form"? I thought we made windows?
Same thing, older name. In Windows Forms, every window is a Form, and every form is an object built from a class (peek at the code later: class Form1 : Form — your class, inheriting a mountain of ready-made window powers). You've been using objects since Console.WriteLine; today you'll finally see one. Classes get their full lecture in Week 9 — today, enjoy the magic.

If I typed nothing… who wrote the code?
Visual Studio did — live, as you clicked. In Solution Explorer, expand the ▸ next to Form1.cs and open Form1.Designer.cs: there's a C# line for every property you just changed (this.Text = "My First GUI — …";). The Designer is a C# code generator with a paintbrush. Rule of the semester: read that file whenever you're curious, but never edit it by hand — your changes get overwritten by the next drag.

Drag your first controls

🎛️— ▢ ✕

Time to furnish the window. From the Toolbox (hover the left edge if it's collapsed, then click the 📌 pin to keep it open), drag these three onto the form, roughly stacked:

  1. A Label near the top — the question your user will read.
  2. A TextBox under it — where they'll type. Drag its side handle to make it comfortably wide.
  3. A Button under that — the thing they'll click.

Notice the pink-and-blue snap lines that appear while dragging — Visual Studio helping you align like a designer. Now give each control a proper identity. Select each one and set two properties:

  • Label → (Name): lblQuestion · Text: What is your name?
  • TextBox → (Name): txtName · (Text stays empty)
  • Button → (Name): btnGreet · Text: Greet me!
💅 Style pass: drag a box around all three controls to select them together, then set Font to Segoe UI, 12pt in one shot. Readable apps get better grades from users and professors.
Why the weird names? What's wrong with button1?
Visual Studio's default names — button1, textBox3 — tell you nothing. In code written months later, btnGreet instantly says I'm a button and I greet. The prefixes are a professional convention you'll use all semester: lbl = Label, txt = TextBox, btn = Button. (Name) is the variable name your C# uses to talk to the control; Text is just what humans see on screen. Two different jobs — mixing them up is this week's #1 bug.
5

Double-click = event

⚡— ▢ ✕

Here comes the biggest idea of the day. In the designer, double-click the btnGreet button. Visual Studio flips from the canvas to Form1.cs — the code view — and has already written this for you:

Form1.cs — Lab03_FirstGUI
private void btnGreet_Click(object sender, EventArgs e)
{
    // your code will go here
}

That's an event handler: a method with a contract — “whenever btnGreet is clicked, run whatever is inside these braces.” Right now it's empty, so clicks do nothing. Not for long.

🧠 The big idea: event-driven programming (read this one!)
Your Lab 1 console programs were a script: line 1, line 2, line 3… done. A GUI program is a vending machine: it starts up, draws itself, and then just waits. It might wait five seconds or five hours. When the user does something — a click, a keypress — Windows fires an event, and the matching handler method runs. Then… back to waiting. You no longer command the timeline; the user does. You just decide what happens in response. Almost every app on your phone works exactly this way.
Two files, one form — what's the split?
Form1.cs and Form1.Designer.cs are two halves of the same class (C# calls this a partial class). The Designer file holds the machine-generated layout code; Form1.cs holds your logic. Clean separation: robots on one side, humans on the other. You will only ever edit Form1.cs.
⚠️ Classic trap: accidentally double-clicked the wrong thing and got a handler you don't want (like Form1_Load)? Don't just delete the method — that can break the Designer. Instead press Ctrl+Z right away, or ask me before surgery. 🩺
6

Make it talk 💬

🗣️— ▢ ✕

Put exactly one line inside the handler (type it — and pause after txtName. to watch IntelliSense list everything the text box can do):

Form1.cs — inside btnGreet_Click
private void btnGreet_Click(object sender, EventArgs e)
{
    MessageBox.Show("Hello, " + txtName.Text + "!");
}

Press F5. Type your name in the box. Click Greet me! — and a pop-up greets you back:

Read that one line like a pro
Three old friends in new clothes. (1) txtName.Text — the dot means look inside: reach into the txtName object and grab its Text property, a string holding whatever the user typed. It's Console.ReadLine()'s cooler cousin — no waiting, the text is just there. (2) The + is your Lab 1 text glue, fusing three strings into one sentence. (3) MessageBox.Show(…) is the GUI world's Console.WriteLine(…) — same shape, but the output arrives as a pop-up instead of a printed line. New stage, same script.

7

Level-up the greeter

✨— ▢ ✕

Pop-ups are fun but needy — they demand an OK click. Real apps usually answer on the window itself. Stop the program (close its window), go back to the designer tab (Form1.cs [Design]), and:

  1. Drag a new Label below the button. Set (Name): lblGreeting, Font: 14pt bold, ForeColor: your pick — and delete everything in its Text so it starts invisible-ish.
  2. Drag a second Button next to the first. (Name): btnClear, Text: Clear.
  3. Double-click Clear to get its own handler, then update both handlers:
Form1.cs — both handlers
private void btnGreet_Click(object sender, EventArgs e)
{
    lblGreeting.Text = "Hello, " + txtName.Text + "! 👋";
}

private void btnClear_Click(object sender, EventArgs e)
{
    txtName.Clear();          // empty the text box
    lblGreeting.Text = "";   // hide the greeting
    txtName.Focus();          // put the cursor back, ready for the next name
}

F5 again. Greet ▸ the label lights up. Clear ▸ everything resets and the cursor jumps home. Two buttons, two events, two personalities.

Properties are a two-way street
In Level 4 you set Text with the Properties panel; now your code sets lblGreeting.Text while the program runs. Reading (txtName.Text on the right of =) and writing (lblGreeting.Text on the left) use the same dot-property — the Designer and your code are just two doors into the same objects. This is the entire secret of GUI programming: read some properties, think, write some properties.
✅ Checkpoint: the greeting appears on the form and Clear resets everything. Bonus experiment: click Greet me! with the box empty — “Hello, !” Slightly tragic. An if statement fixes that in Week 3; remember this moment.

The calculator gets buttons

🧮— ▢ ✕

Remember your Lab 1 console calculator? Same brain — new face. We'll add a second project to the same solution:

  1. In Solution Explorer, right-click the solution line (the very top: Solution 'MAC109_GuiLabs') ▸ Add ▸ New Project… ▸ Windows Forms App (C#) ▸ name it Lab04_GuiCalculator ▸ Create.
  2. Right-click the new Lab04_GuiCalculator project ▸ Set as Startup Project (its name turns bold — that's the one F5 runs).
  3. On its form, build this layout — you know all the moves now:
  • Form Text: MAC 109 Calculator, StartPosition: CenterScreen
  • Two labels: First number: and Second number:
  • Two text boxes: (Name) txtA and txtB
  • Four buttons in a row: btnAdd (Text +), btnSub (−), btnMul (×), btnDiv (÷)
  • One big empty label at the bottom: (Name) lblResult, Font 14pt bold

Double-click the + button and write its handler. Then double-click each remaining button and repeat the pattern, changing only the symbol in quotes and the math at the end:

Form1.cs — Lab04_GuiCalculator
private void btnAdd_Click(object sender, EventArgs e)
{
    double a = Convert.ToDouble(txtA.Text);
    double b = Convert.ToDouble(txtB.Text);
    lblResult.Text = a + " + " + b + " = " + (a + b);
}

// btnSub_Click →  " - "  and  (a - b)
// btnMul_Click →  " * "  and  (a * b)
// btnDiv_Click →  " / "  and  (a / b)
Every line here is a Lab 1 flashback
double — a box for decimal numbers 📦. Convert.ToDouble(…) — the crucial transformation, because txtA.Text is text even when it looks like a number (text-"5" glued to text-"3" is "53", remember? 😱). And those parentheses in (a + b) — still forcing math first, glue second. Delete them in the + handler and run with 12 and 4 if you want to see 12 + 4 = 124 again. The only new ingredient in this whole calculator is the buttons. That's the point: the C# you learned in the console is the C# of every GUI.
🏅 DELIVERABLE #2 — DONE (pending the torture test in Level 9). Four working operations with labeled output — exactly what the rubric wants.
9

Try to break it 😈

🔨— ▢ ✕

F5, then test like a professional — happy path first, sabotage second:

  • 😀 12 and 4: click all four buttons. Clean, labeled answers. Screenshot-worthy.
  • 🔢 7.5 and 2.5: decimals — double handles them like a champion.
  • 🕳️ 10 and 0, then ÷: plot twist — no crash! Doubles shrug and answer ∞ (Infinity). We'll guard this properly with if in Week 3.
  • 🍌 Type banana as the first number, click +: CRASH! Visual Studio dives into the code and highlights the guilty line in yellow: System.FormatException: 'The input string 'banana' was not in a correct format.'
Is crashing… okay?
Today, yes — crashing honestly is fine, and the error message is gold: it names the exception, the reason, and the line. Notice what did not happen: the compiler didn't complain, because Convert.ToDouble(txtA.Text) is perfectly legal C#. This is a runtime error — the code is grammatical but reality (a banana) disagreed. Compile-time vs runtime errors is a quiz question with your name on it. Surviving bad input gracefully (try/catch) is Week 12's superpower.
✅ Checkpoint: you found both limits — Infinity and the banana crash. Real-engineer move: add a // comment at the top of the file noting them. Future-you (and the rubric) will be impressed.

Commit vs push — 15-second refresher
Commit = a labeled snapshot 📸 of your code on this machine. Push = uploading your snapshots to GitHub, where they survive lab-machine amnesia and reach your professor. On a classroom computer, a commit without a push is a photo saved on a camera you're about to hand back.

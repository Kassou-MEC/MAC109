Why (a + b) in parentheses?
Because + runs left to right and the glue chain starts with a number-then-string. Without the parentheses, once " + " enters the chain everything after it glues — you'd get 12 + 4 = 124. The parentheses force the MATH to happen first. This is Example 6's "Total: 52" trap, defeated in the wild.

Break it & fix it — all three bug species, in a GUI

😈— ▢ ✕

This morning you met the three species in the console. Now hunt them in your app — run each sabotage, read the evidence, undo (Ctrl+Z), confirm F5 still works:

  1. 🧊 Compile-time: in any handler, delete Convert.ToDouble( and its closing ), leaving double a = txtA.Text; — instant squiggle, and Problems says CS0029: cannot implicitly convert type 'string' to 'double'. The exact error from the lecture's Example 3, wearing a GUI costume.
  2. 🍌 Runtime: everything compiling? F5, type banana in a number box, click the button. VS Code breaks on the Convert line: System.FormatException. Press ■ Stop. Compiled fine, exploded live — species two.
  3. 👻 Logic: remove the parentheses from your formula — (a + b) in the Add handler, or the grade tool's (g1 + g2 + g3). F5. It runs happily and answers absurdly (12 + 4 = 124 glue, or the infamous 206.7 average). No squiggle, no crash — just wrong. The compiler checks grammar, never intentions.
  4. 🕳️ Bonus: divide by zero once more, on purpose, and wave at ∞. Next week it gets evicted.
The professional ritual, one more time
Compile errors: read the Problems panel top to bottom, fix the FIRST first — later errors are often echoes. Runtime errors: read the exception name and the line it broke on; the answer is usually the input. Logic errors: the only defense is prediction — know the expected answer BEFORE you click. 85/90/95 must average 90; if it doesn't, the code is lying politely.
✅ Checkpoint: everything un-sabotaged, F5 green, all components computing correctly.
